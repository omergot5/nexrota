<objective>
Build the one editing screen this phase needs — a supervisor narrows one person at a time from a full list — and close the assignment route that belongs to tasks rather than shifts.

Purpose: everything before this plan reads a category list that no human can yet produce. This is where the data comes from, and the shape of the editor is the whole of D-03's honesty: the manager sees every category already selected, because that is literally true of a person nobody has touched, and narrows by deselecting. An editor that opened empty and asked the manager to add categories would look identical in code and would mean the exact opposite — it would make an untouched person qualified for nothing.

This plan also closes the assignment route that `03-CONTEXT.md` and QUAL-04's four named routes do not mention but D-02 makes unavoidable. D-02 locks the task's existing category column as the task's qualification field. The task form's assignee picker writes assignments against that column and consults no engine at all today. Leaving it open would mean the product blocks a waiter from the kitchen when the kitchen is a shift and permits it when the kitchen is a task — the same two-blind-spots-in-one-product failure this whole milestone exists to end, and the phase goal says "in no route" rather than "in four routes".

Output: a qualification editor in the roster screen, a qualification gate in the task assignee picker, and the two prop additions their call sites need in `src/components/SupervisorApp.jsx`.

**Decision IDs.** `D-01`…`D-04` are the four locked rows of `03-CONTEXT.md` § "הכרעות נעולות", in order. `P-01`…`P-03` are the three decisions this planning round settled.

- **D-01** — one shared taxonomy. The editor's checklist and the task form's folder input both read `categoryOptions`, the helper plan 03-03 built, so a manager narrows against exactly the vocabulary they assign from.
- **D-02** — the task's existing category column *is* its qualification field, with no second column. This plan is where that becomes true in behaviour rather than only in schema.
- **D-03** — absent and empty both mean unrestricted, and an untouched person must never be represented as a materialised list of every currently-known category. The editor's save rule enforces it: a complete selection saves as unrestricted.
- **D-04** — the manager edits one person separately and narrows their list. There is no bulk editor and no matrix; `REQUIREMENTS.md:59` defers those to `QUAL-V2-02`.

**P-03 — the task assignee picker is treated as a fifth enforcement route, and this plan states that as a decision rather than doing it quietly.** `03-RESEARCH.md` Assumptions Log row A3 flags it at MEDIUM confidence: it is not one of QUAL-04's four named routes, and `03-CONTEXT.md` does not mention it. It is included because D-02 is locked and a qualification field that nothing enforces is not a qualification field, and because the implementation cost is genuinely small — the roster and the task's category are both already in scope in that component. It is enforced as a hard block with no override, matching QUAL-05, and deliberately kept separate from the conflict warning immediately below it in the same form, which *is* overridable with a note and stays exactly as it is. If a reviewer disagrees with including this route, the disagreement is about this paragraph and not about a hidden assumption.
</objective>

One modal, one badge, one normalisation rule that carries the whole decision.

**Step 1 — the props.** Widen `TeamView`'s destructured signature at line 2135 with `shifts` and `tasks`, both defaulting to empty arrays, and pass both at the call site in `src/components/SupervisorApp.jsx` at lines 255-262, where both are already in scope. The editor's checklist must include categories that exist only because a shift or a task uses them, or a manager could not narrow somebody against a category they invented an hour ago — which is most of them, since a category here is a label invented mid-work.

**Step 2 — the modal.** Add local state holding the person currently being edited and the working selection, and a `Modal` that opens from the roster row. Title it with the person's name so the manager knows whose list they are changing — this modal changes one person's access to work and an ambiguous title is how the wrong person gets restricted.

Render the full result of `categoryOptions(shifts, tasks)` as a wrapped row of toggle chips, copying the assignee picker's chip shape at lines 1917-1945: an icon from `folderIcon`, the category name, and a check glyph when selected. Carry the pressed state on each chip so assistive technology reports it, as that picker already does. Every chip is selected when the modal opens for a person carrying no list — that is not a default, it is the truth about that person, and the modal must show the true state rather than an empty form.

For a person who already carries a list, open with exactly the members of that list selected and everything else deselected.

**Step 3 — the save rule, which is the whole decision.** On save, build the selection in the order `categoryOptions` returned it — filter that list by selection rather than accumulating chips in click order — and then apply the rule that matters: if every offered category is selected, save the unrestricted state instead of the list.

Both halves have a reason and neither is cosmetic.

The ordering half is Pitfall 8. Two saves of the same logical selection must produce the same array, or a determinism assertion over stored data compares unequal for no behavioural reason. Building from the canonical list guarantees it; accumulating from click order or from set iteration does not.

The complete-selection half is D-03, and it is the difference between a feature that ages well and one that quietly rots. If selecting everything saved a materialised list of the categories that happened to exist that day, then the next time a manager invents a category on a shift, every person edited before that moment would silently become unqualified for it — a restriction nobody chose, appearing later, attributable to nothing. Saving unrestricted instead means the only people who ever get blocked are the ones a manager deliberately narrowed.

Say that in the modal itself, as a short hint under the chips: a person with everything selected stays unrestricted and will automatically be qualified for categories invented later. It is the one non-obvious consequence of the design and a manager will otherwise reasonably assume the opposite.

Call the action plan 03-02 added; it normalises an empty list to the same unrestricted state at the write end, so the two ends agree by construction rather than by coincidence.

**Step 4 — deselecting everything.** A selection with nothing in it means the same as a selection with everything in it, because both store as unrestricted. That is a real trap: a manager who deselects every chip expecting to block the person entirely would get the opposite. Block the save while nothing is selected, and say why in one Hebrew line — that a person must be able to work at least one kind of work, and that removing them from the team is the action they are reaching for. Do not save and then explain.

**Step 5 — the entry point and the badge.** Add a third `IconBtn` to the roster control cluster at lines 2292-2315, before the removal button, opening the modal for that person. Give it an accessible label naming the person, matching how the exemption toggle's label at lines 2299-2304 is written.

Add a badge to the name block, beside the existing exemption badge at lines 2286-2290, shown only for a person who actually carries a restriction. Word it with the count of categories they may work, and pair it with an icon — the comment two lines above it states this row's rule explicitly, that a coloured dot alone carries no meaning for a colour-blind or screen-reader user. Show nothing at all for an unrestricted person: a badge on everybody is a badge that says nothing, and it would also imply that qualification is something a manager is supposed to configure.

**Step 6 — an untouched roster is unchanged.** Confirm by reading that a team where nobody has been edited renders exactly as before apart from the new button: no badges, no counts, no prompts. Then confirm the round trip by running it — open the modal for an untouched person, save without changing anything, and verify through a reload that the person is still stored as unrestricted rather than as a list. That save-without-changes path is the one most likely to silently materialise a full list, and it is the cheapest place to catch it.
