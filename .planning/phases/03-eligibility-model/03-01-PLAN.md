<objective>
Give the engine a fifth hard-constraint family — qualification — as one pure, load-free helper called first inside `checkHardConstraints`, and prove with Node assertions that it blocks in the engine, refuses with a readable Hebrew reason, cannot be overridden, and never blocks a team that has not been configured.

Purpose: this is the whole phase's load-bearing wall. `checkHardConstraints` (`src/lib/autoAssign.js:183-243`) is already the single choke point for three of QUAL-04's four routes — the greedy fill loop calls it at line 499, `balanceWorkload` at line 616, and `checkAssignment` delegates to it at line 826 for both swap screens. One insertion closes all three. Everything in plans 02, 03 and 04 either stores the data this check reads or shows what this check decided; none of it can be built honestly until the check itself exists and is tested.

Output: two new named exports from `src/lib/autoAssign.js` (`isQualified`, `checkQualification`), one insertion into `checkHardConstraints`, one label added to `explainUnfilled`, one field added to `taskAsShiftShape` in `src/lib/dates.js`, and new `QUAL-` prefixed assertions in both existing verification scripts.

**Decision IDs.** `D-01`…`D-04` are the four locked rows of `03-CONTEXT.md` § "הכרעות נעולות", in order. `P-01`…`P-03` are the three decisions this planning round settled that `03-CONTEXT.md` deliberately left open; each is stated in full in the plan that implements it.

- **D-01** — one shared taxonomy for shift categories and task categories. This plan honours it by giving `isQualified` a single `category` parameter that both entity types feed, and by carrying `category` through `taskAsShiftShape`, the Phase 2 bridge that lets a task be judged by the same code that judges a shift.
- **D-03** — a person with no list is qualified for everything, represented as empty or absent, never as a materialised list of every currently-known category. This plan is where that rule physically lives: `isQualified` treats `null`, `undefined` and the empty array identically, and a work item with no category is unrestricted for everyone. This is the single line that decides whether a brand-new team gets a full schedule on its first run or hits a setup gate.
- **P-01 (this plan, stated here because the engine shape follows from it)** — `checkQualification` takes only a guard and a work item. It takes no roster, no availability map and no rules object, because qualification needs none of them. That narrowness is deliberate and is what makes plan 03-02 able to call it from the manual-assignment path without dragging rest, consecutive-hours and weekly-cap enforcement into a code path that has never had them. `03-RESEARCH.md` § "Open Gap 1" recommends exactly this and flags the alternative — routing manual assignment through the full `checkAssignment` battery — as a larger, separately-reviewable product change. This plan confirms the narrow design rather than silently choosing it.

**Why layered rather than a single vertical slice.** The architecture this phase extends was proven end to end in Phases 1 and 2: a pure engine judged by Node scripts, an `api.js` chokepoint, and React screens that read the result. A thin slice through all three would prove nothing that is not already proven, and the layering here matches the file-ownership boundaries that let the four plans run in four clean waves without two agents editing the same file.
</objective>
