<objective>
Give a person a category list and a shift a work category, carry both across the one file allowed to know column names, and close the fourth QUAL-04 route by gating manual assignment on qualification and on nothing else.

Purpose: plan 03-01 built a check that reads `guard.qualifiedCategories` and `shift.category`. Neither field exists yet. This plan creates both, in a migration that touches no existing row — which is what makes QUAL-02 permanent rather than a promise: every profile and every shift that exists today reads NULL afterwards, and NULL means unrestricted, so a team that has never opened a settings screen is affected by nothing. It is also where the one route `checkHardConstraints` does not cover gets closed.

Output: `supabase/migrations/0006_qualification.sql`, four mapper changes and one new write function in `src/lib/api.js`, a new action and a pre-write gate in `src/hooks/useGuardian.js`, an updated schema document, and mapper assertions in `scripts/verify-planning.mjs`.

**Decision IDs.** `D-01`…`D-04` are the four locked rows of `03-CONTEXT.md` § "הכרעות נעולות", in order. `P-01`…`P-03` are the three decisions this planning round settled that `03-CONTEXT.md` deliberately left open.

- **D-01** — one shared taxonomy. The new shift column is deliberately named and typed identically to the existing task column, and its mappers use the same absent-value conventions, so the two entities Phase 2 unified are described by one vocabulary rather than two that look alike.
- **D-02** — the existing task category column becomes the task's qualification field. No second column is added to the task table by this plan or any other in this phase. The migration is checked for that explicitly.
- **D-03** — absent, `null` and empty all mean unrestricted. This plan is where that becomes a storage fact: the column is nullable with no default, the migration performs no backfill, and the write path normalises an empty list back to NULL so the database never holds two spellings of the same state.
- **D-04** — the manager edits one person at a time and narrows their list. This plan builds the write path that edit uses; plan 03-04 builds the screen.

**P-01 — the manual-assignment gate is qualification-only, and this is a deliberate choice, not an omission.** `03-CONTEXT.md` left this open and `03-RESEARCH.md` § "Open Gap 1" flags it at MEDIUM confidence as a genuine product judgment. The finding underneath it: `toggleAssignment` enforces **no** hard constraint today — not rest, not consecutive hours, not the weekly cap, not even availability. That is a real pre-existing gap, and it is wider than qualification. This plan closes exactly the qualification part of it and no more. Routing manual assignment through the full `checkAssignment` battery would be a larger behaviour change that could refuse assignments a supervisor has always been able to make by hand — covering a hole at 3am that breaks the rest rule because nobody else exists — and that trade-off deserves its own conversation rather than arriving as a side effect of qualification work. The narrow gate satisfies QUAL-04 exactly as worded. The remaining gap must be recorded in the plan summary as an observed, still-open issue rather than left silent.

**P-02 — the person's list is stored as a JSON array column, not as a Postgres text array.** `03-RESEARCH.md` marks this MEDIUM confidence and defensible either way, so the plan states the choice rather than letting the executor guess. Reasons, in order of weight: this schema already stores two person-and-position arrays as JSON columns — the task assignee array added in `0002_task_folders.sql` and the template position array added in `0004_task_templates_and_compatibility.sql` — so a JSON array is the established local idiom and a text array would be the first of its kind in this database; `isQualified` only ever calls an array check and a membership test, so nothing downstream can tell the difference; and the mapper stays a single defensive array check with no driver-specific array parsing. The cost of being wrong is one line in the migration and one in the mapper.
</objective>
