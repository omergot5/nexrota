הוסף `export const ConfirmDialog` ב-`ui.jsx`, ליד `Modal` (אחרי ההגדרה שלה, לפני `Skeleton`). Props: `open, onClose, onConfirm, title, body, confirmLabel = "אישור", cancelLabel = "ביטול", tone = "danger", busy`. `body` הוא node (string או JSX) — לא רק string, כדי שקוראים עתידיים יוכלו להעביר טקסט עם הדגשות אם יצטרכו.

מבנה פנימי, מחקה את `SeedDemoDialog` (views.jsx:64-122) אחד-לאחד, רק מוכלל: `const [pending, setPending] = useState(false);`. `confirm = async () => { setPending(true); try { await onConfirm(); } finally { setPending(false); } onClose(); }`. `closeUnlessPending = () => { if (!pending) onClose(); }`.

רנדר: `<Modal open={open} onClose={closeUnlessPending} title={title} footer={<><Btn variant={tone} onClick={confirm} loading={busy || pending} className="flex-1">{confirmLabel}</Btn><Btn variant="secondary" onClick={closeUnlessPending} disabled={pending}>{cancelLabel}</Btn></>}><div className="text-sm text-content">{body}</div></Modal>`.

`tone` נופל ישירות ל-`variant` של `Btn` — לא ממציא מיפוי נוסף. ברירת המחדל `"danger"` מתאימה לרוב הצרכנים (מחיקות/דריסות); קוראים שצריכים טון אחר (פרסום, שהוא הפיך-בקושי ולא מחיקת-נתונים לפי 12-CONTEXT.md ממצא §4) יעבירו `tone="accent"`/`tone="outline"` במפורש ב-12-03/04.

הוסף בלוק-הערה קצר מעל הרכיב שמסביר: (1) למה "ביטול" לעולם לא קורא ל-onConfirm — אף אחת מהפעולות שהרכיב הזה עוטף לא מציירת patch אופטימי לפני האישור (CONFIRM-06, 12-CONTEXT.md open_questions #4), אז "ביטול" הוא ניקוי-state טהור, לא ביטול-פעולה-שכבר-קרתה; (2) ש-`pending` הוא הכללה של הדפוס שכבר הוכח ב-`SeedDemoDialog`, לא מנגנון חדש.
