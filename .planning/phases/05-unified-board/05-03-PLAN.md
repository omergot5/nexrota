<planner_decisions>
- **No extension to `positions.js`.** RESEARCH.md's `<board02_positions>` verified the module in full: it never reads `Date.now()` or `new Date()`, every sort is explicit, and `plannedRowsForWeek` is a pure function of its two arguments. Four weeks is four calls. A new library function here would be a second implementation of branching logic that D-01 of phase 4 deliberately centralised.
- **Realized vs. planned is derived, not stored.** `missingRowsForWeek(position, sundayISO, realized)` already answers "which planned rows do not exist yet" for one week, matching on `positionId` and identity date. Use it per week rather than re-deriving the comparison, so the forecast and the auto-creation path can never disagree about what "already exists" means.
- **Tap target on a not-yet-realized row.** D-07 says editing only. The row has no database identity yet, so the only thing there is to edit is the position's *definition* — the same `Modal` the pencil button on the card already opens. The forecast row therefore calls the card's existing `onEdit` and nothing else. This is also what keeps D-08 true: there is no second action anywhere on the surface to accidentally add one next to.
</planner_decisions>

Add a new section to `scripts/verify-positions.mjs`, after the existing sections, headed for BOARD-02 in the same comment style the file already uses. Reuse the file's existing `check` helper and its seeded `shuffle`; add no framework and no shared fixture file — this codebase has neither, and each verify script is self-contained by convention.

Fixtures: a fixed Sunday literal such as `"2026-09-06"` (never a value derived from the current clock), the four Sundays at day offsets 0, 7, 14 and 21 computed with `addDays`, one template-shape position with a few weekdays selected and both hours set, and one weekly-shape position.

Assertions to add:

  - **Four distinct week sets, template shape.** Calling `plannedRowsForWeek(templatePos, sundayN)` for the four Sundays yields four row sets whose identity dates are pairwise disjoint — no date appears in two weeks. This is the property the forecast's correctness rests on, and it is what a naive re-implementation would break first.
  - **Four distinct week sets, weekly shape.** The same for the weekly position: each week yields exactly one row, and the four rows' `dueDate` values are four distinct Saturdays, each exactly six days after its own Sunday.
  - **Shape invariants survive across weeks.** Every template row across all four weeks carries the position's hours and a `date`; every weekly row across all four weeks carries `startDate` equal to that week's Sunday, `dueDate` equal to that week's Saturday, and both time fields null. Assert the null-ness explicitly — a forecast that ever printed an hour for a weekly position would be inventing data.
  - **Determinism across the whole four-week projection.** Building the full four-week projection three times in a row stringifies identically; and building it after passing deterministically shuffled copies of any array input stringifies identically to the unshuffled build.
  - **Realized-versus-planned separation.** Given a `realized` array holding rows for exactly one of the four weeks, `missingRowsForWeek` returns empty for that week and the full planned set for the other three; and a row belonging to a *different* `positionId` on the same date does not suppress anything, which is the POS-04 rule the existing module comment states.
  - **No clock dependency.** The same four-week projection computed from a Sunday far in the past and from a Sunday far in the future both return the same row *count* and the same relative day offsets — the result depends on the argument, not on when the test runs.
  </action>

**Data.** Derive the four Sundays as `addDays(sundayISO, n * 7)` for n from 0 to 3, where `sundayISO` is the card's existing `weekDates[0]`. For each Sunday, call `plannedRowsForWeek(position, sunday)` for the full planned set and `missingRowsForWeek(position, sunday, realizedRows)` for the subset that does not exist yet, where `realizedRows` is the concatenation of the `shifts` and `tasks` the card already receives. **Structure.** Four sequential sub-sections, one per week, in chronological order, inside the existing card — no horizontal strip, no carousel, no swipe. Each week gets a compact heading naming its range via the existing `rangeLabelHe(weekFrom(sunday))` helper, with the current week distinguishable by wording rather than by colour alone. The section as a whole gets the `t("positions.forward")` heading with an existing icon from the registry, matching the heading shape the two POS-05 lists already use.

**Rows.** One shared row rendering for both position shapes (D-06). Let the row's own data imply the difference: a template row shows its date and its hours; a weekly row shows its week span and no hours. Do not branch on `position.shape` to pick a different row component, a different icon family or a different colour — that branch is exactly what D-06 forbids, and the data already distinguishes the two.

**The planned badge.** A row that has not been realized yet carries `Badge` with `tone="neutral"` and the `t("positions.planned")` text. A realized row carries no extra badge — the same "a badge marks only the exception" instinct `TaskRow` states about itself. Give the planned badge a `title` that says plainly that the row will be created automatically when the week arrives and that there is nothing to configure; a manager who reads "מתוכנן" and cannot tell whether they must act has been given a puzzle, not information.

**Interaction.** A not-yet-realized row is a button whose only effect is to call the card's existing `onEdit` — the position definition modal (D-07). A realized row is not interactive at all on this surface (D-08). There must be no assign control, no toggle, no disable control and no delete control anywhere in this section.

**Empty week.** A week whose planned set is empty — a template position whose weekdays do not land in that week, or an inactive position — renders the muted line `"אין שורות מתוכננות השבוע הזה"` in `text-muted`, never in a warn or danger tone and never inside an `Alert`. An empty forecast week is a normal fact about the position's schedule.

**No fetch.** Everything on this surface is computed from props the card already holds. Add no loading skeleton and no error branch.
