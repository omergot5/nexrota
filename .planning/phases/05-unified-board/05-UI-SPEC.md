## Spacing Scale

**Exception to the generic 8-point/4px-multiple guidance, stated explicitly:** this codebase's shipped spacing system uses Tailwind's half-step (2px-granularity) values throughout its glass-density components — `p-2.5` (10px), `p-3.5` (14px), `gap-1.5` (6px) appear pervasively in `ui.jsx`, `views.jsx`, and the exact QUAL-08 blocks this phase must reuse **verbatim** (D-09). Introducing a strict 4px-only grid for the new board would visually clash with the reused QUAL-08 markup on the same screen. Phase 5 matches the existing scale rather than a textbook 8pt grid.

| Token | Value | Usage |
|-------|-------|-------|
| 1.5 | 6px | Icon-to-label gaps inside a badge/chip (`gap-1.5`) — matches `Badge`, QUAL-08 lock chip |
| 2 | 8px | Row-internal icon/text gaps (`gap-2`) |
| 2.5 | 10px | Compact row padding (`p-2.5`) — matches `TaskRow`, `AssignView` candidate buttons |
| 3 | 12px | Gap between a day-group header and its list; horizontal gap between list rows |
| 3.5 | 14px | Denser card padding (`p-3.5`) — matches `FairnessLine`, `EmptyState` choice buttons |
| 4 | 16px | Standard board-row padding (`p-4`) — matches `GuardApp`'s duty cards |
| 5 | 20px | `Card` default padding (`p-5`) — top-level board section container |
| 6 | 24px | Vertical rhythm between major board regions (`space-y-6`) — matches `MySchedule`, `WeekFlow` |

Exceptions: none beyond the half-step note above — this **is** the established scale, not a deviation from it.

## Typography

Reuses the app-wide scale exactly (no new sizes introduced). 4 sizes, 2 primary weights for this phase's new work — see weight exception note below the table.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label (meta: time, date, count, badge text) | 11px (`text-[11px]`) | 600 semibold | 1.3 (`leading-snug`), numeric fields get `data-numeric` for tabular figures |
| Body (item title, row primary text) | 14px (`text-sm`) | 600 semibold for the item's own label; 400 regular for secondary description text on the same row | 1.4 |
| Heading (day-group header, position card title) | 16px (`text-base`, browser default under this stack) | 700 bold | 1.2 |
| Display (screen-level page title, only where `PageHeader` is used, e.g. the "calendar" tab if repointed — see Open Recommendation below) | 24px (`text-2xl`) | 700 bold, `tracking-tight` | 1.2 |

**Weight exception:** this phase's own new rows/badges/labels use exactly two weights — 400 (regular, secondary text) and 600 (semibold, primary/label text) — matching `TaskRow`/`AssignView`/`PositionCard` row-level typography. 700 (bold) is listed for Heading/Display only because it is the **pre-existing, unchanged** weight already used by `PageHeader`'s `<h1>` and `Card`'s `<h3>` app-wide; Phase 5 does not introduce a third weight, it inherits one that already exists at a structural level this phase's rows don't touch.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--bg` / `--bg-deep` (cream `#F6F4E8` light, `#0C211E` "יער" dark) | Page background beneath every board surface |
| Secondary (30%) | `--surface` / `--surface-sunken` (glass white 78%–97% alpha / sunken tint) | Day-group section cards, board list rows, position-forecast cards, badges' neutral background |
| Accent (10%) | `--brand` / `--brand-strong` (`#2E7365` / `#1E5B50`) | Reserved for exactly: (1) the board's own `PrimaryAction` CTA button, (2) the "today" day-group header highlight (reusing `WeekCalendar`'s existing `bg-brand/10` + `text-brand` today convention, ported from grid cell to list-row header), (3) an active/selected navigation or step state if the board is mounted as a `WeekFlow` step |
| Destructive | `--danger` (`#B02A21`) | **Not used anywhere on this phase's board surfaces.** D-08 makes the position board read-only and D-03 keeps all delete/edit actions in the existing `TaskMgmt`/`ShiftMgmt`/`PositionsScreen` screens, unchanged. `--danger` stays reserved for those existing delete buttons only — the board itself never renders it. |

**Accent reserved for:** the three uses above — never for shift/task item background color (that is `shiftTone()`'s existing time-of-day scale — morning→night, an orthogonal system, unchanged and applied identically to both shifts and engine-eligible tasks per `withEngineTasks`), and never to visually distinguish a shift-type item from a task-type item (explicitly forbidden by **D-12**).

**Second semantic color — `--warn` (`#9E5806`):** reserved for the missing-coverage indicator on an under-staffed shift row, porting `WeekCalendar`'s existing "חסרים N" language (icon + text + `ring-warn`, `Icon name="alert"`) from a grid block to a vertical list row, since D-16 forbids the grid layout but says nothing about the coverage-warning vocabulary itself.

**Neutral (`ring-hairline-strong` + `bg-surface-sunken`, never `ring-danger`):** reserved for exactly two states, both reused verbatim from existing precedent, never invented fresh: the qualification-block treatment (**D-09**, QUAL-08) and the "מחוץ למנוע" (engine-ineligible) badge (`TaskRow` precedent, `views.jsx:1769-1777`).

**Per-guard identity color (`guardColor()`, 10-hue set in `ui.jsx`):** orthogonal to this 60/30/10 surface contract — unchanged, reused wherever a guard's avatar or name-chip appears on the board (e.g. `People`/`Avatar` components), exactly as `PositionCard` and `TaskRow` already use it.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (board's own `PrimaryAction`, if mounted as a `WeekFlow` step) | First-person, matches existing step-0 tone (`"בניתי את השבוע — מי הגיש?"`) — recommended: **"המשך לבניית השבוע"**, `hint`: dynamic count e.g. `"${N} פריטים השבוע"` when non-empty, or omitted when the board is empty (empty state below already explains next action) |
| Empty state heading — manager board, zero shifts+tasks+timeless items this week | **"השבוע עדיין ריק"** |
| Empty state body — manager board | **"בנה משמרות או משימות, והלוח ייבנה מעצמו — או תתחיל מ'תסדר לי את השבוע'."** (worded as an invitation per **D-15**, not a warning; reuses `WeekCalendar`'s existing tone: `"בנה את השבוע או מלא אותו מתבנית, והלוח ייבנה מעצמו"`) |
| Empty state heading — guard board, zero items assigned this week | **"אין לך כלום השבוע"** |
| Empty state body — guard board | **"כשתשובץ למשמרת, למשימה או לעמדה — היא תופיע כאן."** (reuses `MySchedule`'s existing two-branch empty copy pattern — published-yet vs. not-published-yet — see `GuardApp.jsx:192-198`; keep both branches, this phase only extends the *check* to include tasks/timeless items, not the copy shape) |
| Empty state — position, zero rows in a given forecast week (e.g. a `template` position with no weekdays landing in that week) | **"אין שורות מתוכננות השבוע הזה"**, muted tone (`text-muted`), never an alert — an empty forecast week is a normal fact about the position's schedule, not a problem |
| Error state | **N/A — no new copy.** The board introduces no independent data fetch (confirmed: `shifts`/`tasks`/`positions` arrive as already-loaded props from `useGuardian`); load failures continue to surface through the existing global error banner. Do not add a board-specific error string. |
| Qualification-block label (per assignee, on any board item) | **Exact reuse, verbatim, no new copy:** `"לא כשיר/ה"` + lock icon (`Icon name="lock"`) + neutral ring — the literal QUAL-08 string from `views.jsx:1159-1160` / `2112-2116`. Do not paraphrase. |
| Engine-ineligible ("timeless") item badge | **Exact reuse, verbatim, no new copy:** `Badge tone="neutral" icon="lock"` reading `"מחוץ למנוע"`, tooltip reusing the existing sentence from `TaskRow` (`views.jsx:1771`). Do not invent a "all-day" or "no time" label — omission of the clock icon/time text is itself the signal (see UI Considerations, long-text/overflow note). |
| Position forecast — not-yet-realized row badge (**D-07**) | New copy, one word, neutral tone: **"מתוכנן"** (planned) — signals "this row will exist automatically, nothing to configure," distinct from a realized row which carries no extra badge (same "badge only marks the exception state" instinct as `TaskRow`'s `!eligible` badge) |
| Position forecast — not-yet-realized row tap target (**D-07**) | Opens the existing position-edit `Modal` (the position's *definition*, not a per-row action — the row itself has no database identity yet) |
| Destructive confirmation | **None.** This phase adds no destructive action anywhere on the board (**D-03**: task/shift editing stays in existing screens; **D-08**: position board is read-only). No `UndoBar`/confirm copy is introduced by Phase 5. |

**New `terms.js` keys implied by the above** (for planner/executor — additions only, `BASE` + no `army` override unless noted): `nav.board` (recommended civil: `"השבוע במבט אחד"`; recommend an `army` override consistent with existing military register, e.g. `"תמונת מצב שבועית"`), `positions.forward` (recommended: `"4 השבועות הקרובים"`), `positions.planned` (recommended: `"מתוכנן"`). All other strings above reuse existing keys/literals unchanged — do not duplicate `"לא כשיר/ה"` or `"מחוץ למנוע"` as new `terms.js` entries; they are inline literals in `views.jsx` today and should stay sourced from the one QUAL-08/TaskRow location, not re-declared.

## Layout & Interaction Contract (board-specific — supplements the generic template sections above)

This section is not part of the template's standard headings but is required for the checker and the
executor to have an unambiguous row-level spec, given D-16's constraint ("vertical list, not grouped by
hour") has no prior precedent in this codebase to point to verbatim.

**BOARD-01 — unified list structure (manager `WeekFlow` step 0 and guard `MySchedule`, same component):**
- One continuous vertical list for the week, **grouped by day** (day grouping is date-based, not
  hour/period-based, so it does not violate D-16 — D-16 forbids grouping *within* a day by hour block).
- Each day group: a sticky-optional (not required) header row — weekday name + short date
  (`DAYS_HE_SHORT` + `shortDate()`, matching `WeekCalendar`'s header convention) + an inline coverage
  badge only when relevant (missing-coverage count in `--warn`, or nothing when fully covered — never a
  redundant "OK" badge on every day, matching `TaskRow`'s "badge only marks the exception" instinct).
  "Today" gets the `--brand` tint per the Color section above.
- Within a day: **timeless items first** (frozen/multi-day/weekly-position tasks — RESEARCH.md
  Assumption A1, adopted as the contract here — sort order like an all-day-event convention), **then
  timed items ascending by `startTime`** (existing `.sort((a,b)=>a.date.localeCompare(b.date)||
  a.startTime.localeCompare(b.startTime))` convention, e.g. `GuardApp.jsx:134`).
- Row visual language is **identical for shifts and engine-eligible tasks** (D-12): item label, time range
  with clock icon (timed) or date range with calendar icon + `"מחוץ למנוע"` badge (timeless), assignee
  avatars (`People`/`Avatar`), and — only when applicable — the per-assignee QUAL-08 lock treatment.
  The one and only legitimate visual differentiator between rows is content (label/time/people), never a
  category-of-item color or icon family.
- Qualification block is rendered **per assignee**, not per item (**D-11**, resolved HIGH-confidence in
  RESEARCH.md §3): a multi-assignee item with one blocked person shows that one person's avatar/chip with
  the lock + `"לא כשיר/ה"` treatment while the other assignees render normally.
- Only assignees literally present in the item's `assignedGuards`/`assignees` array get scanned for
  qualification — the board never proactively computes "would guard X be blocked" for people not already
  on the item (**D-10**).

**BOARD-02 — position forward board (`PositionsScreen`'s `PositionCard`, extended):**
- 4 week-groups per position, each computed via `plannedRowsForWeek(position, sundayISO)` called with
  `sundayISO` at `n*7` day offsets, `n = 0..3` — reusing `positions.js` unchanged (no library extension
  needed, per RESEARCH.md `<board02_positions>`).
- One shared row rendering for both position shapes (`template`/`weekly`) — **D-06** — no shape-specific
  visual branch beyond what the row's own data already implies (a `template` row has hours, a `weekly`
  row spans the week; both render through the same row component as any other board item).
- Not-yet-realized rows (from `plannedRowsForWeek` directly, not yet present in `shifts`/`tasks`) carry
  the `"מתוכנן"` badge and route a tap to the position's edit `Modal` only (**D-07**) — no assign/toggle
  affordance anywhere on this surface (**D-08**, fully read-only).
- Realized rows (already-materialized `shifts`/`tasks` matched by `positionId`) render through the same
  row component BOARD-01 uses — no second row template.

throughout `ui.jsx`/`views.jsx` (e.g. `TaskRow`'s `<span className="... truncate">`), inherited unchanged.

## Open Recommendation (flagged, not a locked decision — for planner confirmation)

RESEARCH.md's Open Question 1 (does the "calendar" nav tab keep a week-mode after Phase 5?) is not
resolved by CONTEXT.md. For visual-contract consistency with **BOARD-04**'s single-source-of-truth
acceptance test, this UI-SPEC recommends: repoint the "calendar" tab's week-mode `Segmented` option to
render the same unified-board component (E1) rather than deleting it or leaving the old shift-only
`WeekCalendar.jsx` mounted there unchanged — a second, inconsistent "week" view directly undermines
BOARD-01's "no two screens to cross-reference" success criterion. Month view (`CalendarView.jsx`) is
unaffected either way. This is a recommendation the planner should explicitly accept or override, not an
implicit default.
