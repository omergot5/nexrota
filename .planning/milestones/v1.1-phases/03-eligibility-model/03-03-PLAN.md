<objective>
Give a shift the category field the engine now reads, make the manual assignment grid show who may not work it and why, and fix the swap-legality call that would otherwise treat every guard as qualified for everything.

Purpose: after plan 03-02 the block is real but invisible. A supervisor clicking a person and getting an error banner with no prior signal is a worse product than no blocking at all — QUAL-07 exists precisely to stop that. This plan is also where a bug found during research gets fixed: the guard-side swap screen passes a synthetic object carrying only an identifier into the legality check, so the moment qualification data exists that screen would approve every swap regardless of the person's real profile, while the supervisor's screen — which resolves the full record — correctly refuses the identical request. Two devices, one request, opposite answers.

Output: a shared category-suggestion helper and a category field on the shift form in `src/components/supervisor/views.jsx`, a locked candidate treatment and a blocked-count line in the assignment grid, and a one-line correction in `src/components/GuardApp.jsx`.

**Decision IDs.** `D-01`…`D-04` are the four locked rows of `03-CONTEXT.md` § "הכרעות נעולות", in order. `P-01`…`P-03` are the three decisions this planning round settled.

- **D-01** — one shared taxonomy. This plan builds the single helper that produces it, and points the shift form at it. Plan 03-04 points the task form and the qualification editor at the same helper.
- **D-03** — a person with no list is qualified for everything. The grid must render that person as an ordinary clickable candidate with no new decoration, or the screen would teach managers that the feature needs configuring when it does not.
</objective>

One helper, one prop, one field.

**Step 1 — the shared helper.** Add `categoryOptions(shifts, tasks)` at module scope in `views.jsx`, immediately below `folderIcon` so it sits with the rest of the taxonomy code and next to the JSDoc that explains what a category is in this product.

It collects every truthy category string appearing on either array, then returns the shortcut folder names in their declared order followed by every collected name that is not a shortcut, sorted. Return the shortcut names in full rather than filtering them to those in use: this list is a suggestion list for an input and, in plan 03-04, the full checklist for the qualification editor, so a shortcut nobody has used yet must still be offerable. That is the one way this differs from `TaskMgmt`'s folder grouping at lines 1541-1561, which filters because it is grouping actual rows rather than offering choices — leave that computation exactly as it is.

Order deterministically and never from raw set iteration: shortcuts in declared order, then the remainder sorted. `03-RESEARCH.md` names this as Pitfall 8 — the qualification editor in plan 03-04 saves an array built from this list, and two code paths that build the same logical list in two different orders produce arrays that compare unequal and would make a determinism assertion flake intermittently. Both arguments must default to empty arrays and the helper must survive a null entry in either, because it is called from four components with four different prop availabilities.

Write a short Hebrew comment above it stating that this is the one shared taxonomy D-01 requires: the shift form, the task form and the qualification editor all read their vocabulary from here, so a manager who invents a category on a shift sees it offered when they narrow somebody's qualifications, and the two screens cannot drift into two vocabularies that merely look alike.

**Step 2 — the prop.** Widen `ShiftMgmt`'s destructured signature at line 272 with a `tasks` parameter defaulting to an empty array. `WeekFlow`'s shared prop bag already passes it, so no call site changes — confirm that by reading `WeekFlow.jsx` lines 99-104 rather than assuming it.

**Step 3 — the form field.** Add a category entry to the `blank` literal at lines 278-281, defaulting to the empty string. Empty is the decision, not an oversight: a shift with no category is unrestricted for everyone, so no default may be guessed — guessing one would restrict people against a category the manager never chose.

`openEdit` at line 297 spreads the whole shift, so an existing category arrives with no change there. Confirm that by reading rather than assuming, since a future refactor to an explicit field list would silently drop it.

Add the field to the form modal, immediately below the two-column grid at lines 732-762 and above the shift-length line at 764-767 — after the shift's identity and timing are settled and before the summary. Copy the task folder input's control shape exactly: an `Input` with a `list` attribute pointing at a `datalist`, whose options come from `categoryOptions(shifts, tasks)`. Give the datalist an element id distinct from the task form's, since both components can be mounted in the same document.

Label it in Hebrew as the kind of work, and give it a hint saying two things a manager cannot infer: that this is what qualification is checked against, and that leaving it empty means everyone may work the shift. That second half is the sentence that stops a manager filling the field defensively on every shift because they assume empty is unsafe.

**Step 4 — copying a day carries the category.** `runSpread` at lines 358-382 copies a day's shift *definition* onto other days — label, times, type, colour, location, headcount. Leave `applyTemplate` alone for the same reason — it patches times, type and label only.

**Step 5 — do not touch the conflict matrix.** The category string now feeds two independent mechanisms: qualification, which asks whether a person may ever do this kind of work, and the existing compatibility matrix, which asks whether two kinds of work may sit on one person in one window. They share a vocabulary and nothing else. Do not route the new field through `compatIndex`, `pairRule` or `findConflicts`, and do not add a category argument to any of them. Add a one-line comment near the new field recording that the two are separate, since the surface similarity is exactly what invites someone to merge them.
