<objective>
Give the constraint engine and the conflict matrix one shared notion of a time window, and let a single-day task that carries hours participate in the existing load bookkeeping without a second code path.

Today `checkHardConstraints` (`src/lib/autoAssign.js:171`) only ever sees shifts and `findConflicts` (`src/lib/conflicts.js:67`) only ever sees tasks, each with its own private overlap test — `autoAssign.js:162` compares absolute milliseconds with strict `<`, `conflicts.js:59` compares ISO date strings with inclusive `<=`. A person can hold a full-day kitchen task and a night shift on the same day and neither engine notices. This plan closes that at the engine layer: one `windowsOverlap`, one task-to-shift adapter, and the existing constraint and load functions fed rather than rewritten.

Purpose: the product must agree with itself. Two engines that measure the same week with two different rulers is the same class of defect Phase 1 just closed for fairness weights — this time between shifts and tasks.

Output: six new exports in `src/lib/dates.js`, a rewired `taskWindow`/overlap path in `conflicts.js`, a `tasks` parameter on `autoAssign` and `checkAssignment`, and new `UNIF-0N ·` assertion blocks in both verification scripts.

**Decision IDs.** `02-CONTEXT.md` § "הכרעות נעולות" is a table numbered 1–6 without IDs; rows 1–6 map to D-01…D-06 in order. D-07, D-08 and D-09 are resolved by this plan set because `02-RESEARCH.md` flagged them as open and the discuss-phase never covered them.

- **D-01** — only a single-day task may carry hours and enter the engine; a multi-day task stays frozen outside it
- **D-02** — one overlap function (`windowsOverlap`), two input resolutions; a date-only window is normalised to a full calendar day before comparison
- **D-03** — the "frozen" badge appears only on frozen tasks, never on active ones (implemented in plan 02-03)
- **D-04** — the "frozen" badge appears everywhere a frozen task is displayed (implemented in plan 02-03, bounded by D-08)
- **D-05** — the hour fields in the new-task form open empty, with no default (implemented in plan 02-02)
- **D-06** — `gs_task_templates` gains no default-hour fields this cycle (honoured in plan 02-02)
- **D-07** *(resolved here, `02-RESEARCH.md` Open Question 1)* — a task's load weight is flat `LOAD_WEIGHTS.default`, **not** a night multiplier inferred from its clock hours. `shiftLoad` reads `LOAD_WEIGHTS[shift.type]`, and `type` is a categorical field a shift *declares*; it is never inferred from the clock, not even for shifts. A task has no such field, and inventing time-of-day inference for tasks would give the task side a rule the shift side does not have — the opposite of unification. The weekend multiplier still applies automatically and unchanged, because `isWeekendShift` is derived from `date` and `startTime`, both of which the adapter supplies. This is the literal reading of UNIF-02's "בדיוק כמו משמרת": the same load *pipeline*, not a new inference.
- **D-08** *(resolved in plan 02-03, `02-RESEARCH.md` Open Question 2)* — D-04's "everywhere" is bounded to the surfaces that exist today
- **D-09** *(resolved here)* — a task's `status` does **not** affect engine eligibility. A task marked done still counts toward rest, consecutive hours, the weekly cap and load, because the hours were actually worked and ticking a checkbox does not undo them. This does not contradict `conflicts.js`'s existing `status === "done"` skip: that skip answers a different question — whether two *categories* collide — and it is left byte-identical for UNIF-06.
</objective>
