<planner_decisions>
- **D-11 resolved (per-assignee, not per-item)** — adopted from RESEARCH.md §3 at HIGH confidence. Both existing multi-assignee treatments in this codebase (`AssignView`'s guard grid, `TaskMgmt`'s assignee-chip picker) apply QUAL-08 per person. There is zero precedent for an item-level flag; `qualBlocked` in the task form is a save gate, not a display convention, and even it names the specific blocked people. An item-level ring would be a new visual language the moment it shipped, contradicting D-09's "בדיוק את הטיפול מ-QUAL-08".
- **RESEARCH.md Assumption A3 adopted** — the guard sees the same QUAL-08 signal on their own item that the manager sees. Rationale: D-02 makes the unified board cover both sides, and the alternative is a duty the participant can no longer explain to themselves. This is the low-risk direction: the guard already knows they are on the item; the treatment only makes the reason legible.
- **P-04 — `NextDuty` stays timed-only.** The hero card renders a countdown built from `shiftInterval(shift)` and prints `startTime}–{endTime`; a timeless item can supply neither. The hero therefore selects the first *timed* upcoming item, and timeless items always live in the list below. Fabricating a time to promote a timeless item into the hero is the exact anti-pattern the milestone's out-of-scope table forbids.
- **P-06 — the guard's date window.** `MySchedule` today shows all upcoming duties, not just the current week; narrowing that to seven days would hide next week's shifts and would be a regression against the participant's single question, "מתי אני עובד". So the guard passes `UnifiedBoard` a `dates` list built from the distinct anchor dates of its own items from today forward, sorted ascending. `boardItemsForDates` takes the list as an argument and stays pure (P-05, plan 05-01).
</planner_decisions>

Scope the check exactly as D-10 requires: iterate only the people whose ids are already in `item.assignedGuards`. Do not iterate the team and ask who *would* be blocked; the board reports a state that exists, it does not run a hypothetical.

The signal, per person, is the four-part treatment read from `AssignView` — all four, because three of them are deliberately redundant:

  3. a lock glyph — the `lock` icon at size 11 with `strokeWidth={2.5}` — sits on the avatar in the same absolutely-positioned chip shape the source uses, with the same surface ring so it reads on any row colour;
  4. the neutral ring pair `ring-hairline-strong` with `bg-surface-sunken`. The danger ring must not appear: an unqualified person is a fact about the person, not an error the viewer caused, and collapsing the two visually is the exact regression QUAL-08 was written to prevent.

Carry the refusal sentence into the chip's `title` using the same phrasing `AssignView` builds — the one that names the category — so the board and the manual-assignment screen cannot describe the same refusal in two different sentences.

Because a board row renders its people through `People`, extend that component (in `views.jsx` it is already being exported for the board) with an optional per-person predicate — for example a `blockedIds` set or an `isBlocked(guard)` callback — and apply the four signals to just those avatars. Keep the existing behaviour byte-identical when the new prop is absent, so `TaskRow` and every other current caller is unaffected.

The treatment must be applied by the same code path regardless of whether the item originated as a shift, an engine-eligible task, or a timeless task. If a branch on item type appears anywhere near this logic, the BOARD-03 promise has already been broken.
